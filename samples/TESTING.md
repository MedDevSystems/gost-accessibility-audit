# Стратегия валидации проверок на реальных сайтах

Зафиксировано в разговоре 2026-05-23. Это living document — править,
когда меняются сами правила (а не данные, которые им подчиняются).

---

## Миссия

Инструмент должен по нажатию одной кнопки выдать **обоснованный вердикт**
по каждому пункту ГОСТ для произвольной живой веб-страницы. «Обоснованный»
означает: слепой/слабовидящий аудитор или разработчик, прочитав вывод,
понимает **что именно** проверено, **что найдено**, и **что с этим делать**.

Универсальность алгоритмов — не «инструмент работает на сайтах из списка».
Это **«инструмент не имеет понятия о существовании конкретных сайтов»**.
Его единственный вход — `Snapshot`; что в этом снимке (wildberries или
localhost) — для логики проверок невидимо.

## Три непреклонных принципа

1. **Универсальность.** Алгоритмы не должны содержать знания о конкретных
   сайтах. Единственный вход — `Snapshot`; поле `snapshot.url` — это
   метаданные, не условие ветвления. Проверка: переименуйте
   `snapshot.url` с `wildberries.ru` на `example-shop.com` → результаты
   должны быть идентичны.
2. **Каждый вердикт обоснован.** И FAIL, и PASS несут reasoning:
   «Не пройдено, потому что X» / «Пройдено, потому что проверено Y
   и обнаружено соответствие». Тихий PASS без сбора данных — это баг.
3. **Нехватка данных = UNCERTAIN, не PASS.** Если в снимке нет данных,
   необходимых для решения по критерию, вердикт — UNCERTAIN с
   обоснованием «Не могу сказать, потому что…». Никогда PASS по
   умолчанию (легаси-антипаттерн 3.3.1: «формы не найдены — не
   применимо → PASS»).

## Требования к качеству вердиктов

**Каждый вердикт — это пара (verdict, reasoning).** Сейчас в коде
reasoning есть только в FAIL-ветке (через `longDescription` + `evidence`).
В PASS-ветке — пусто. Нужно добавить:

- **PASS-обоснование**: «PageLang: соответствует — lang="ru-RU" валиден
  по BCP 47, primary subtag = ru». Аудитор должен видеть **что именно
  проверено и почему пройдено**, а не просто галочку.
- **UNCERTAIN-обоснование**: «KeyboardAccess: не могу гарантировать —
  найдено 12 div[onclick] без role, но JS-обработчики addEventListener
  я не вижу из снимка. Требуется ручная проверка с клавиатуры».

**Каждый дефект — это (defect, evidence, recommendation).** Тут стандарт
уже держится: селектор + html-фрагмент + ссылка на ГОСТ и WCAG technique.

**Никакого «галочного» PASS без сбора данных.** Если данных
недостаточно для вердикта — это UNCERTAIN с явной причиной, а не PASS.

## Требования к универсальности

Принцип «не точить под сайт» нужно конкретизировать, чтобы он не
становился отговоркой:

| Что МОЖНО | Что НЕЛЬЗЯ |
|---|---|
| Расширять словарь паттернов: добавить «перейти к навигации» в список skip-link фраз — это **расширение универсальности**, не сужение | Хардкодить `if (location.host === 'wildberries.ru')` — даже намёк → отказ |
| Понижать ложноположительные. Пример: image alt="Tag: 2024" сейчас ловится как meaningless по регексу `^\d+$`. Меняем регекс — лучше для ВСЕХ сайтов | Демпфировать severity ради «чтобы на WB не было слишком много» — false positive нужно ЧИНИТЬ, а не глушить |
| Добавлять данные в Snapshot: `shadowDomImages`, `iframeImages` — добивать слепые зоны коллектора | Игнорировать дефект только потому что он «технически нарушение, но в этой индустрии так принято» — это уже точка зрения автора стандарта, не наша |

**Тест на универсальность простой**: «если я переименую сайт в
snapshot.url с wildberries.ru на example-shop.com — поменяются ли
результаты?». Должно быть **нет**.

## Что и как измерять

Без чисел «улучшаем универсальность» — пустая фраза.

Для каждой проверки на каждой странице корпуса фиксируем четыре исхода:

1. **TP** (true positive) — проверка вернула FAIL, ручной аудит
   согласен «это действительно нарушение»
2. **FP** (false positive) — FAIL, но ручной аудит говорит «всё в
   порядке, это не нарушение»
3. **TN** (true negative) — PASS, ручной аудит согласен «нарушений нет»
4. **FN** (false negative) — PASS, но ручной аудит нашёл нарушение,
   которое мы пропустили

Из этого:
- **Precision** = TP / (TP + FP) — «сколько FAIL'ов реальны»
- **Recall** = TP / (TP + FN) — «сколько реальных нарушений мы поймали»

### Целевые метрики (зафиксированы)

| Проверка | Precision | Recall | Почему |
|---|---|---|---|
| Бинарные структурные (PageLang, PageTitle, ViewportZoom, SkipLink) | ≥ 0.95 | ≥ 0.95 | Однозначные, должны быть почти безошибочны |
| axe-обёртки (Contrast, LinkText, ValidHTML, Aria, Autoplay, FormLabels) | ≥ 0.90 | ≥ 0.85 | axe — отраслевой стандарт, доверяемся его precision; recall ниже, потому что axe не покрывает 100% кейсов |
| Эвристики (CaptchaPresence, HeadingStructure, KeyboardAccess) | ≥ 0.80 | ≥ 0.70 | Тут эвристики, заведомо менее точны; границы шире |
| Ещё не добавлено: ColorOnly, TextInImages, FormErrors, Focus* | TBD после первой реализации | TBD | Сначала измерить, потом ставить цель |

Без таких чисел разговор «универсально/не универсально» — субъективный.

## Когда применять LLM

«30 фиксов» — рабочая эвристика, но содержательный критерий:
**LLM рассматриваем когда исчерпан класс задач, решаемых формальной
логикой**.

LLM **показан** тогда, когда вопрос проверки звучит как
«**имеет ли смысл этот текст в этом контексте?**»:
- ImgAlt: «alt='Schedule of meetings' содержательный или нет?» —
  формально не отличить от мусорного alt
- ColorOnly: «эта ссылка выделена только цветом, или цвет — просто
  акцент, а семантика передаётся ещё чем-то?» — нужно «понять»
  окружающий контекст
- TextInImages: «на этой картинке есть текст, который должен был быть
  прописан в HTML?» — нужно vision

LLM **НЕ показан** когда вопрос — «**соответствует ли значение
формальному правилу?**»:
- Lang валиден по BCP 47 — regex
- Title не пустой — `length > 0`
- Контраст 4.5:1 — axe считает арифметически
- Дублирующиеся id — `Set.has`

### Конкретный критерий запуска LLM-обсуждения для проверки X

Все четыре условия должны выполниться:

1. Реализована формальная версия
2. Прогнана на корпусе ≥ 10 сайтов с ручной разметкой
3. Precision < 0.7 ИЛИ recall < 0.5 после ≥ 2 итераций тюнинга
4. Анализ FP/FN показывает, что **большинство ошибок — про «смысл»**,
   а не про «полноту данных в snapshot»

Если условие 4 не выполняется — добавляем данных в snapshot, не LLM.
Если выполняется — обсуждаем LLM серьёзно: где (CLI fallback /
опционально в расширении), какая модель, как с privacy.

## Антипаттерны — явный список

Чтобы потом не спорить «это патч или универсальное улучшение»:

1. **Site-specific код** — любое упоминание конкретного домена/префикса
   URL в `lib/`. Даже намёк → отказ.
2. **Demote severity to mute** — переводить дефект из Critical в Minor
   «чтобы не пугать на маркетплейсах».
3. **Silent PASS** — `return []` без понимания почему. Если данные
   не собраны → UNCERTAIN.
4. **Vocabulary через blacklist под сайт** — «исключить из meaningless
   паттернов слово X, потому что на сайте Y оно нормально».
5. **«Это редкий кейс»** как причина игнорирования — пока ручной аудит
   на корпусе подтверждает, что это реальное нарушение, оно должно
   ловиться.
6. **Тюнинг на одной странице** — изменение, валидированное только на
   vos.org.ru, не считается изменением. Минимум 3 разные страницы
   (разные домены, разные движки) должны подтвердить улучшение.

## Жизненный цикл проверки

Каждая проверка проходит стадии. Стадии трекаются в `manual-audit.md`,
секция «Per-check stage tracker».

1. **Draft** — реализована, unit-тесты зелёные на синтетических
   фикстурах. (На момент 2026-05-23 у нас 14 проверок здесь.)
2. **Validation** — прогнана на корпусе ≥ 5 живых страниц через
   расширение, **результат каждого FAIL и каждого PASS вручную
   помечен TP/FP/TN/FN** в `manual-audit.md`. Самая нудная стадия —
   без неё нет метрик.
3. **Tuning** — несколько итераций «правка алгоритма → пере-прогон →
   пересчёт TP/FP». Итерация засчитывается только если precision
   и recall **не ухудшились на других страницах корпуса** (защита
   от over-fit).
4. **Stable** — после N итераций без изменений и метрики выше
   целевых → проверка «зрелая». Можно понижать частоту регрессионных
   прогонов.
5. **Escalation** — если в Tuning не сходимся → решаем:
   LLM / переосмысление scope / частичный отказ («ловим 60% случаев,
   помечаем как best-effort»).

Идея: **в каждый момент времени по каждой проверке мы знаем её
стадию**.

## Артефакты, по которым видно что цели достигнуты

Конкретные результаты, которые мы хотим в конце итеративной фазы:

1. **Корпус из 15-20 реальных сайтов** разного типа (госсайт,
   маркетплейс, новостной портал, SPA, статический, корпоративный).
   Каждый — `samples/html/<name>.html` (через `pnpm grab-html` или
   ручной capture из живого Chrome когда headless заблокирован).
2. **Таблица ручной разметки** `samples/manual-audit.md`: для каждого
   сайта × каждой проверки — TP/FP/TN/FN с краткой причиной
   (1 строка). Это работа аудитора-эксперта, не разработчика.
3. **Метрики precision/recall** в `samples/metrics.json`,
   авто-генерируемые скриптом `pnpm corpus-metrics` (надо написать
   когда таблица набирёт 30+ строк).
4. **Регрессионный страж**: тест в CI, который запускает корпус-аудит,
   сравнивает с baseline JSON, падает если precision или recall
   упали > 5 п.п.
5. **Журнал «трудных» проверок** — отдельный документ с записями про
   каждую проверку, у которой precision < target. Содержит: примеры
   FP/FN, гипотезы, попытки фиксов, решение (продолжить тюнить /
   escalate / accept).

### Как захватить страницу, до которой Playwright headless не доходит

Когда `grab-html` падает с `ERR_CONNECTION_CLOSED` или похожим
(антибот), варианты:

1. **Через расширение** — самый простой: открыть страницу в Chrome
   (с куки / залогиненная сессия если нужно) → DevTools →
   GOST A11y → Запустить аудит → «Скачать снимок». Это даёт
   `snapshot.json` — для воспроизведения локально мне HTML
   не нужен, на снимке работает `pnpm audit-snapshot`.
2. **DevTools → Elements → правый клик на `<html>` → Edit as HTML →**
   копировать → сохранить в `.html`.
3. **Chrome → More tools → Save page as → Webpage, HTML Only**.

Дальше `pnpm gost-audit "file://$(realpath samples/html/your.html)"`
прогоняет аудит на захваченной странице.

## Ручная ground-truth таблица

`samples/manual-audit.md` хранит человеком-проверенный вердикт
для каждой пары (страница, проверка). Это источник истины, против
которого считаются precision/recall.

Формат: одна строка на пару, колонки: page, check, automated-verdict,
ground-truth, TP/FP/TN/FN, notes.

Колонка «Notes» — самая ценная: она объясняет ПОЧЕМУ алгоритм был
прав или не прав. Без неё цифры precision/recall теряют смысл
при следующей итерации.

## Метрики (планируется автоматизировать)

Будущий скрипт `pnpm corpus-metrics`:
1. Парсит `manual-audit.md`
2. Для каждой проверки считает precision/recall из строк
3. Эмитит `samples/metrics.json`
4. Печатает таблицу «текущее vs целевое»

Не реализовано — добавится когда таблица набирёт хотя бы 30 записей,
до того smysl автоматизировать невелик.

## Регрессионный страж (планируется)

Будущий vitest integration test:
1. Пере-аудитит каждый HTML-файл в `samples/html/`
2. Diff JSON отчётов с `samples/baseline/*.json`
3. Падает если число дефектов изменилось неожиданно

Добавится после первого цикла tuning, когда стабилизируются базовые
ожидания.
